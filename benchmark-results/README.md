# Benchmark Evidence Policy

This directory is for **reviewed, reproducible performance evidence**, not ad-hoc local output.

## Directory policy

Local scratch runs belong under:

```text
benchmark-results/local/
```

That path is intentionally ignored by Git.

Only reviewed evidence that is tied to a specific Git revision and documented machine should be copied under:

```text
benchmark-results/curated/
```

Recommended layout:

```text
benchmark-results/curated/
  YYYY-MM-DD-<short-sha>-<machine-name>/
    ENVIRONMENT.md
    keepalive-c8/
      summary.json
      paired-analysis.json
      threadpool-run-01-client.json
      threadpool-run-01-server.json
      threadpool-run-01-client.log
      threadpool-run-01-server.log
      ...
      epoll-run-05-server.log
    connect-c64/
      ...
```

## Required environment metadata

Every curated result set must include `ENVIRONMENT.md` containing at least:

- exact Git SHA,
- whether the working tree was clean,
- build command and configuration,
- compiler and version,
- CPU model,
- physical/logical core count when known,
- RAM,
- OS distribution/version,
- kernel version,
- power/performance mode when known,
- whether the client ran on the same machine or a remote machine,
- whether Linux is native, WSL2, or another VM,
- relevant background workload notes,
- exact comparison commands,
- reasons for any invalidated/excluded runs.

## Raw evidence rule

Do not commit only `summary.json`.

A curated scenario must retain every raw file generated by `tools/compare_runtimes.py` for the repetitions being reported:

- client JSON,
- server JSON,
- client logs,
- server logs,
- summary JSON.

Failed or saturated runs are evidence too. They must not be silently deleted to improve the headline result.

## Comparison rule

When comparing `threadpool` and Linux `epoll`:

- use the same benchmark-server binary,
- use the same Git revision,
- use the same `/bench` handler/payload,
- use the same client mode/request count/concurrency/warm-up/timeout,
- use the same total admission budget,
- repeat each runtime/scenario at least five times,
- report failure/rejection behavior alongside throughput and latency,
- use medians rather than selecting the single best run.

## Paired mathematical analysis

After a comparison directory contains complete threadpool/epoll repetitions, run:

```bash
python3 tools/analyze_runtime_pairs.py benchmark-results/local/comparison \
  --output benchmark-results/local/comparison/paired-analysis.json
```

The analyzer pairs runs by repetition index and calculates the per-pair epoll-vs-threadpool percentage change for:

- successful requests per second;
- successful-request p95 latency;
- successful-request p99 latency;
- failure rate when the threadpool baseline is non-zero.

It then reports the median paired percentage change and how consistently the direction appears across repetitions. Positive throughput delta means epoll measured higher; negative latency delta means epoll measured lower.

This is intentionally a descriptive paired analysis, not a claim of statistical significance or a universal runtime winner. The final conclusion must remain scoped to the documented machine and scenario.

## Claims rule

Curated local loopback evidence may support a statement such as:

> On the documented machine and workload, runtime A measured higher/lower than runtime B under the recorded conditions.

It does **not** automatically support claims such as:

- production ready,
- internet scale,
- handles N users,
- universally X% faster,
- lower latency on other hardware,
- better for blocking handlers or static-file workloads that were not measured.

Any percentage comparison must be reproducible from the committed raw evidence and accompanied by the tested scenario and machine limits.

## CI is not benchmark evidence

The GitHub Actions runtime-comparison smoke exists only to verify that the comparison tooling works end to end. Hosted-runner throughput/latency from that smoke must not be copied into this curated directory or cited as project performance evidence.
